# Putting Unmask on the internet — Render + MongoDB Atlas + Cloudflare R2

Written 27 September 2026, from the deployment that was actually attempted that day: the
site on Vercel (`unmask-seven.vercel.app`), the API on Render, both databases still on a
laptop. Every claim here was checked against the code in this repository or against a
command that was run.

---

## 1. The one rule that decides everything else

**The site and the API must be reached at the same address.**

Not "same server" — same *address in the browser's address bar*. This is not a
preference; it is how the two halves were built:

| Where | What it does | Why it forces one address |
|---|---|---|
| `web/src/api.js` | every call is `fetch('/api/...')` | a relative path resolves against the page, so the site asks **its own host** for the API. There is no "API base URL" setting, and `web/scripts/no-foreign-origins.js` fails the build if any absolute off-origin URL appears in the bundle |
| `web/src/socket.js` | `wss://<the page's own host>/ws` | chat is a WebSocket, and a WebSocket has no way to carry a token in a header |
| `api/src/services/sessions.js` | `httpOnly, sameSite=lax, secure in production` | the login session is a cookie. From one address it is first-party and gets sent; from two addresses it is a third-party cookie, which Safari refuses outright and Chrome is phasing out. There is no fallback, deliberately: a session key in a URL lands in proxy logs and browser history, and this one lasts 30 days |

So **a site on Vercel and an API on Render cannot work together** — not "not yet", not
"needs one more setting". The page would ask Vercel for `/api/auth/login`, and Vercel has
no API. Even if you pointed the browser at Render directly, the chat socket would be a
cross-site connection carrying no cookie, and `api/src/realtime.js` would answer the
handshake with 403 — which is the correct answer, because the alternative is letting any
website open a signed-in student's chat.

The fix is one process serving both, which is what `api/src/app.js` already does when it
finds a built site next to itself. Vercel then has no job. Keep it or delete it; either
way it is not part of the running site.

## 2. MongoDB Atlas (the database, off the laptop)

The code already speaks Atlas natively — `api/src/db.js` passes a `mongodb+srv://` string
to Mongoose 8 and allows 10 seconds for the SRV lookup and TLS handshake a laptop
container never needs.

1. <https://www.mongodb.com/cloud/atlas/register> → **M0 free cluster**. Pick a region;
   write down which one (see §5, POPIA).
2. **Database Access** → Add new user → role **Read and write to any database** → a
   password generated by Atlas. That password's only job is to let the API talk to this
   cluster.
3. **Network Access** → Allow Access From Anywhere (`0.0.0.0/0`). Render's documentation
   is explicit that the free instance type includes **no dedicated outbound IP**, so there
   is no address to list; if the service is ever on a plan that publishes one, put that
   address in this list instead and drop the wide-open line. Read §6 — this is the one
   decision here that trades a safety for a convenience.
4. **Connect** → Drivers → copy the string. It arrives with **no database named**, and
   this project insists on one: insert `/unmask` before the `?`, so the path reads
   `...@cluster0.xxxx.mongodb.net/unmask?retryWrites=true&w=majority`. Without it
   `api/scripts/backupLib.js` throws `MONGO_URL names no database` and the backup scripts
   stop, which is the behaviour you want from a tool about to write to a database.

**What is already in this repository for Atlas:** `api/src/db.js` reports which host it
could not reach, `api/src/index.js` prints provider advice rather than "is the container
running?" for a database that is not on this machine (both proven in
`test/boot.test.js`), and `test/backup.test.js` parses a real SRV string and proves the
password never reaches a printed message.

## 3. Cloudflare R2 (the photos, off the laptop)

`api/src/services/photo-store/` picks a driver from `PHOTO_STORE`; `r2.js` talks to R2's
S3-compatible XML API. It signs each request with `node:crypto` and sends it with the
`fetch` Node 24 already has, so there is no AWS SDK in `package.json` and nothing to
install — which also means there is no SDK version to drift from what
`test/photoStoreR2.test.js` proves. Nothing about the privacy rules moved with the bytes:
no custom domain is connected to the bucket, so a photo has no URL a browser could be
given, and the API streams the bytes out itself after `api/src/services/reveal.js` says
both students agreed.

1. <https://dash.cloudflare.com/?to=/:account/r2> → **Create bucket** → a name
   (`unmask-storage`) → **Location** left on *Automatic*, or a hint. The **Settings** tab
   of the finished bucket prints its **S3 API** address,
   `https://<account-id>.r2.cloudflarestorage.com/<bucket>`. Copy it, and write down the
   location (§5).
2. Under **Account Details → API Tokens → Manage** → **Create Account API token** →
   permission **Object Read & Write**, scoped to that one bucket → copy the **Access Key
   ID** and the **Secret Access Key**. The secret is shown once.
3. **These two are not the `cfat_…` token.** A `cfat_` value is a Cloudflare *account*
   API token: it speaks the management API, which can create and delete buckets. The S3
   pair above speaks only the objects inside the buckets it was scoped to. If
   `R2_ACCESS_KEY_ID` starts with `cfat_`, the wrong string is in the wrong place.
4. A **jurisdiction** bucket (EU, US, FedRAMP) lives at a different host —
   `https://<account-id>.<jurisdiction>.r2.cloudflarestorage.com` — and a bucket's
   jurisdiction cannot be chosen again after it is created. If the bucket has one, put
   that host in `R2_ENDPOINT`.

The variables, all six, go in `UNMASK\.env` and in Render's environment:
`PHOTO_STORE=r2`, `R2_ENDPOINT` (or `R2_ACCOUNT_ID`, from which the API builds the
endpoint), `R2_BUCKET`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, and optionally
`R2_TIMEOUT_MS` (8000 by default). Paste the values into the file rather than retyping
them, and never send the Access Key ID, the Secret Access Key or the bucket's endpoint
into a chat message or a screenshot — the second of the three is the whole bucket in one
string, a student's face included.

Two things the driver does that are worth knowing about, because they turn a mysterious
failure into a named one: `/api/health` reports a wrong key and a missing bucket
differently (`"unauthorized"` against `"bucket-not-found"`, both asserted in
`test/photoStoreR2.test.js`), and a store that stops answering is given up on after
`R2_TIMEOUT_MS` rather than being allowed to hang the request that showed somebody's
profile.

## 4. Render (the one process)

Your deploy log's eight lines were eight boot gates refusing a broken deployment, which is
what they are for. Seven were correctly named. The eighth — "copy `.env.example` to
`.env`" — sent you to a file a PaaS never has; fixed on 27 September, and it now lists
only the keys genuinely missing and says to put them in the host's environment instead.

| Setting | Value |
|---|---|
| Root Directory | *(leave the repository root)* |
| Build command | `npm run setup && npm run build` |
| Start command | `npm start` |
| Environment | everything below |

`npm run setup` installs the API's and the site's dependencies; `npm run build` compiles
the site into `web\dist`, which is what lets the API serve it. Without that second half
`WEB_DIST` is empty and `SERVE_WEB` silently stays off: JSON with no site.

| Variable | Value | Why the gate exists |
|---|---|---|
| `MONGO_URL` | the Atlas string from §2, with `/unmask` in the path | nothing can be read or saved |
| `SESSION_SECRET` | 64 hex characters: `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"` | under 32 characters a login cookie is forgeable |
| `PUBLIC_APP_URL` | `https://<your-service>.onrender.com` — no trailing slash | the cookie is `Secure` in production, so an `http` address means every login looks like a wrong password |
| `WEB_ORIGIN` | **exactly the same value** | it is both the browser allowlist and the chat-socket allowlist. Set it wrong and only chat breaks, quietly |
| `TRUST_PROXY_HOPS` | `1` | Render terminates TLS; with `0` every student arrives as one address and one person's wrong passwords lock out the whole campus |
| `PHOTO_STORE` | `r2` | an image rebuild wipes everything inside the container, photos included. A typo here is refused at boot rather than guessed at |
| `R2_ACCOUNT_ID` (or `R2_ENDPOINT`) `R2_BUCKET` `R2_ACCESS_KEY_ID` `R2_SECRET_ACCESS_KEY` | from §3 — `R2_ACCOUNT_ID` alone builds the endpoint; `R2_ENDPOINT` is the form to use if the bucket has a jurisdiction in its address | asked for whenever `PHOTO_STORE=r2`, in any environment — and an `http://` endpoint is refused on its own, because every photo request signs its secret into that line |
| `BREVO_API_KEY` `MAIL_FROM` | the key headed **API key** in Brevo's settings (it starts `xkeysib-`, and it is a different string from the SMTP key) · the address Brevo lists as **Verified** under *Senders, Domains and IPs* | this is the only mail door that works here. See the note below the table |
| ~~`SMTP_HOST` `SMTP_PORT` `SMTP_USER` `SMTP_PASSWORD`~~ | **leave every one of these empty on Render's free tier** | Render blocks outbound traffic to ports 25, 465 and 587 (their changelog, 26 September 2025). Filling this block in is the one configuration mistake on this host that no boot gate can catch: the process boots, prints `email via smtp-relay.brevo.com`, reports `"emailTransport": "smtp"` as if it were working, and then hangs for two minutes on every single registration before answering `Something went wrong on our end.` |

`BREVO_API_URL` needs no entry — the default is Brevo's own address, and setting it to
an `http://` value is refused at boot, because the key rides in that request's headers.

The SMTP block is not dead code: it is the door for a server that is allowed to open a
socket, such as your own machine behind a university relay. `BREVO_API_KEY` simply wins
when both are set, because a machine configured for both is a machine that meant to use
the one that reaches the internet.

`SERVE_WEB` needs no entry: with no value the API serves the build if there is one.
`NODE_ENV=production` is set by Render itself, which is what switches the gates on.

Then read <`https://<your-service>.onrender.com/api/health`>. It answers booleans and
nothing else — no URL, no path, no key, asserted by a test — and it is the place to look
when a page misbehaves:

```
"readiness": { "database": true, "sessionSigning": true, "emailTransport": "brevo-http",
               "activeInstitutions": 5, "photoStore": { "backend": "r2", "writable": true } }
```

`"emailTransport"` names the door a code actually leaves by: `brevo-http` is the HTTPS
relay and the only correct answer on this host, `smtp` means a relay was configured and
is *probably* unreachable here, and `local-outbox` on a public URL means neither block
is filled in and no student can finish registering.
`"activeInstitutions": 0` means no address at any college can register — run §7.
`"photoStore": { "writable": false }` means the bucket or the key is wrong, and `reason`
names which: `unauthorized` is the key pair, `bucket-not-found` is the name, and
`unreachable` is the endpoint or the network.

## 5. Two sentences about South African law

POPIA s72 covers sending personal data outside the country for processing. A student's
confirmed address, their faculty, their chat messages and their face are personal data,
and the two hosts put them somewhere you can name but did not fully choose: Atlas has a
region dropdown, so pick it on purpose, while R2 places a bucket automatically *near the
request that created it* unless a jurisdiction (`eu`, `us`, `fedramp`) is chosen at
creation — and that choice cannot be changed afterwards, so decide it before the first
photo lands. Nothing here is illegal — an Information Officer's responsible decision,
done knowingly, is what the section asks for — but the operator's registration condition
says processing happens "within the Republic", so write down the Atlas region and the
R2 placement, and name both in `/privacy` (the page reads its text from the database, so
staff can edit it without a deploy). Neither provider offers a South African location.

## 6. What these choices cost

Written down because a free tier that is not described is a surprise scheduled for later.

- **`0.0.0.0/0` in Atlas' allow list** leaves one thing guarding the whole database: the
  password from §2. On a private network the allow list is the second lock; here there is
  no second lock. Render does offer dedicated outbound IPs for a workspace
  (`render.com/docs/outbound-ip-addresses`); when this service has one, list it in Atlas
  and the wide-open line goes away.
- **M0 is 512 MB on shared hardware with no automated backups.** `NFR-5.2`'s "automated
  daily backups" is met by the scripts in this repository, which have to be *run* — §7 —
  not by Atlas. **M0 is also not the 2,000 concurrent students of `NFR-1.3`**; it is
  enough for a pilot at one campus.
- **Render spins down a Free web service that goes 15 minutes without inbound traffic**,
  so the first student after a quiet quarter-hour waits through a cold start, and an open
  chat socket does not count as inbound traffic — a conversation can end in a reconnect.
  A rebuild also costs every byte inside the container, which is the whole reason the
  photos are in R2 and the database is in Atlas rather than on that machine.
- **R2's free tier is 10 GB-month of storage, 1 million write operations and 10 million
  read operations a month, and it charges nothing for egress** — that last one is why the
  API can stream every photo to a browser itself instead of handing out a URL. At a few
  hundred kilobytes per re-encrypted photo (the browser resizes before uploading,
  `web/src/encodePhoto.js`) 10 GB is tens of thousands of pictures, and a student viewing
  their own match is one read. Beyond the free tier the published rate is $0.015 per
  GB-month plus a fraction of a cent per thousand reads, so the number to watch is the
  object count, not the traffic.
- **A bucket backup is one download per photo.** `npm run backup` copies every object
  into its folder, so with hundreds of students it is a minute of small files, not a
  second. It is the honest cost of not storing the bytes where the database is; the
  alternative — letting the bucket hold the only copy — is a backup that silently misses
  half the data, which is why the manifest records which store each set came from
  (`test/backup.test.js` proves the label matches the store that was actually read).

## 7. After the first successful boot, in this order

1. **Put the institutions in.** A brand-new database has no colleges, and every domain
   check fails before it reaches a mailbox, so registration refuses every address. Aim
   `MONGO_URL` in `UNMASK\.env` at Atlas on the laptop and run `npm run seed`. It refuses
   to run with `NODE_ENV=production` — that is a stage-2 gate doing its job — so it is
   done from here, once. It writes five institutions **and four demo students plus one
   reviewer**, all on the password `unmask-demo-2026`. Set `DEMO_PASSWORD` to something of
   your own while you do, or delete those five accounts from the staff screen before
   anyone else is told the address exists.
2. **Make a real reviewer.** Sign up with your own address through the site, then
   `npm run staff you@mycput.ac.za` on the laptop, with `MONGO_URL` pointing at Atlas.
   That is how `thando.test1@mycput.ac.za` got its admin role on 27 September — which is
   also why signing up that address again did not change its password.
3. **Back it up, and restore the backup to prove it.** From the laptop, against Atlas:
   install the MongoDB Database Tools once and set `MONGODUMP_BIN` to `mongodump`'s path,
   which is the switch `api/scripts/backupLib.js` already reads — with it, the Docker step
   this project needed on a laptop disappears. Then `npm run backup -- --to D:\backups`,
   and once a month the `restore.js` line against the newest folder. A backup that has
   never been restored is a file with a claim on it.
4. **Only then tell a student the address exists.** Until §5 and §6 are decided on paper,
   the honest description of this deployment is a public pilot, not a launch.
